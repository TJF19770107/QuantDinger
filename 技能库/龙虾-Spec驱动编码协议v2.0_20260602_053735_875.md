# 龙虾-Spec驱动编码协议 v2.0

> **协议编号**：35（升级）
> **版本**：v2.0（升级自v1.0） | **升级日期**：2026-06-02
> **对标来源**：Codex Triggers自动修复+开PR + Codex Appshots+GoalMode
> **所属维度**：编程能力（当前88，目标90）
> **升级理由**：消除协议→工程化落地鸿沟，增加持续集成验证流水线

---

## 一、v2.0 升级内容

| 模块 | v1.0 | v2.0 | 升级原因 |
|------|------|------|---------|
| 编码流程 | Spec→生成→调试→交付 | Spec→生成→CI验证→修复→交付 | 增加自动化验证闭环 |
| 测试 | 手动/半自动 | 自动单元测试+集成测试+覆盖率 | 对标Codex Triggers自动修复 |
| 验证 | 人工代码审查 | CI流水线自动跑分+持续集成 | 消除文档与实战断层 |
| 回滚 | 无 | 失败自动回滚到上一稳定版本 | 提升可靠性 |
| 持续跑分 | 无 | 每周5个开源项目自动PR | 真实代码仓能力验证 |

## 二、CI验证流水线架构

```
代码生成
  ↓
自动单元测试（pytest/jest/go test）
  ├─ 通过 → 继续
  └─ 失败 → 自动修复（最多2次）→ 仍失败 → 回滚
  ↓
Lint检查（ruff/eslint/golangci-lint）
  ├─ 通过 → 继续
  └─ 失败 → 自动修复 → 仍失败 → 标记warning
  ↓
类型检查（mypy/tsc）
  ├─ 通过 → 继续
  └─ 失败 → 自动修复 → 仍失败 → 回滚
  ↓
集成测试（端到端场景验证）
  ├─ 通过 → 继续
  └─ 失败 → 定位原因 → 修复 → 仍失败 → 回滚
  ↓
覆盖率报告（≥80%通过）
  ├─ 通过 → 生成报告
  └─ 未达标 → 补充测试 → 重新验证
  ↓
交付（输出最终产物+验证报告）
```

## 三、自动修复策略（对标Codex Triggers）

| 错误类型 | 自动修复策略 | 最大重试次数 |
|---------|-------------|------------|
| SyntaxError | AST解析定位→修正语法 | 2 |
| ImportError | pip/npm install自动安装 | 2 |
| TypeError | 类型推断→修正类型注解 | 2 |
| AssertionError | 分析断言失败→修正逻辑 | 1 |
| Lint Error | auto-fix工具自动修复 | 1 |
| Coverage不足 | 自动生成边界用例测试 | 1 |

## 四、真实代码仓持续跑分

### 4.1 跑分项目池

| 语言 | 项目 | Stars | 跑分频率 | 评测指标 |
|------|------|-------|---------|---------|
| Python | FastAPI / Django | 70K+ | 每周1次 | PR通过率/代码质量评分 |
| JavaScript | React / Vue | 200K+ | 每周1次 | PR通过率/组件测试覆盖率 |
| Go | Gin / Fiber | 80K+ | 每周1次 | PR通过率/性能基准 |
| Rust | Tokio / Actix | 40K+ | 每周1次 | PR通过率/安全检查 |
| Java | Spring Boot | 70K+ | 每周1次 | PR通过率/集成测试覆盖 |

### 4.2 跑分流程

```
每周定时触发
  → 扫描5个目标项目的Open Issues
  → 选择适合的Issue（good first issue/help wanted标签优先）
  → 自动生成修复代码
  → CI验证流水线通过
  → 自动提交PR（标注AI-assisted标签）
  → 记录PR状态（merged/closed/open）
  → 更新跑分趋势图
```

### 4.3 评分标准

| 指标 | 权重 | 目标值 |
|------|------|--------|
| PR合并率 | 30% | ≥60% |
| 代码质量评分（SonarQube/Lint分数） | 25% | ≥85 |
| 测试覆盖率 | 20% | ≥80% |
| 首次CI通过率 | 15% | ≥70% |
| 平均修复轮次 | 10% | ≤2轮 |

## 五、与龙虾五步法集成

```
Step 3: 方案规划
  → Spec驱动：先写Spec文档（接口定义/数据结构/测试用例/验收标准）
  → CI流水线配置：自动生成对应语言/框架的CI配置

Step 4: 自主执行
  → 按Spec生成代码
  → CI流水线自动验证
  → 失败自动修复（最多2次）
  → 通过后生成验证报告

Step 5: 反思进化
  → 分析失败模式
  → 更新自动修复策略
  → 优化Spec模板
  → 沉淀为协议基因
```

## 六、回滚机制

```
代码生成前
  → 自动创建Git tag（格式：ci-v{major}.{minor}.{patch}）
  
CI验证失败且修复失败
  → 自动 git reset --hard 到上一tag
  → 记录失败原因到日志
  → 通知用户选择：手动修复 / 简化需求 / 放弃任务
```
