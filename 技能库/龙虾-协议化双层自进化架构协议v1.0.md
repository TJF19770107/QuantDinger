## 一、协议概述

协议化双层自进化架构协议定义了面向智能体自我进化的双层协议架构。底层RSPL（资源状态协议层）对Agent内部五类资源进行统一建模和生命周期管理；上层SEPL（自进化协议层）定义Propose→Evaluate→Commit闭环，确保每一次自进化操作可追踪、可回滚、可审计。

---

## 二、双层协议架构

### 2.1 RSPL：资源状态协议层（Resource State Protocol Layer）

对Agent内部五类资源进行统一建模：

| 资源类型 | 标识 | 状态模型 | 版本控制 |
|---------|------|---------|---------|
| Prompt | P | draft→review→active→deprecated | 语义版本号(v1.0/v1.1/v2.0) |
| Agent | A | initialized→running→paused→terminated | 配置版本化 |
| Tool | T | registered→verified→active→suspended | 接口版本锁定 |
| Environment | E | provisioned→configured→ready→destroyed | 环境快照 |
| Memory | M | raw→indexed→curated→archived | 内容哈希+时间戳 |

每类资源必须在RSPL中注册，获得唯一资源ID和当前状态。所有变更必须经过状态机合法转换。

### 2.2 SEPL：自进化协议层（Self-Evolution Protocol Layer）

定义标准化的自进化三阶段闭环：

```
Propose(提议) → Evaluate(评估) → Commit(提交)
     ↑                                  |
     └────────── Rollback(回滚) ←───────┘
```

| 阶段 | 动作 | 产物 |
|------|------|------|
| Propose | 分析任务反馈→生成进化提案→标记影响资源 | Evolution Proposal JSON |
| Evaluate | 沙箱评估→性能测试→安全检查→评审审批 | Evaluation Report |
| Commit | 通过后提交变更→更新RSPL→记录审计日志→打标签 | Commit Record + Git Tag |
| Rollback | 失败时回滚到上一个稳定版本→通知受影响组件 | Rollback Record |

## 三、五类资源统一建模

### 3.1 资源注册规范
```json
{
  "resource_id": "P-001",
  "resource_type": "prompt",
  "version": "v1.2",
  "status": "active",
  "dependencies": ["A-003", "T-007"],
  "created_at": "",
  "updated_at": "",
  "checksum": "sha256:..."
}
```

### 3.2 版本化接口
- 每次Propose必须递增资源版本号
- 旧版本保留在RSPL中，标记为deprecated
- Commit后自动生成Changelog Diff

## 四、执行规范

### 4.1 Propose规范
1. 进化提案必须包含：影响资源列表、预期收益、风险评估、回滚方案
2. 提案ID格式：EVO-{timestamp}-{resource_type}-{increment}
3. 涉及多资源的提案，必须标记依赖顺序

### 4.2 Evaluate规范
1. 必须在隔离沙箱中评估，禁止在生产环境直接测试
2. 评估指标：性能变化/安全合规/功能正确性/资源消耗
3. 不通过评估的提案必须记录失败原因后拒绝

### 4.3 Commit/Rollback规范
1. Commit前必须生成完整审计日志（who/what/when/why/how）
2. Rollback必须恢复所有受影响资源到上一个稳定版本
3. 连续3次Rollback触发熔断，暂停该资源方向的进化

---

## 五、安全约束

1. 自进化操作必须经过Human-in-the-loop审批（🔴高风险变更）
2. RSPL中的资源状态变更必须记录不可篡改的审计链
3. 沙箱评估环境必须与生产环境完全隔离
4. 涉及系统提示词或安全策略的Propose，必须经独立安全Agent审核
