## 一、协议目标

在多 Agent 协作中建立三层知识库体系，确保所有 Agent 在同一规则下协作，避免越界和冲突。

---

## 二、三层架构定义

```
L1-项目宪法（Project Constitution）
    • 技术选型
    • 整体架构决策
    • 不可变的长期原则
    • 需求约束

L2-领域规则（Domain Rules）
    • 模块边界定义
    • 跨模块协作协议
    • 接口契约
    • 命名规范

L3-细节对齐（Detail Alignment）
    • 接口字段
    • 参数格式
    • 返回值规范
    • 版本号
```

---

## 三、读写权限矩阵

| 角色 | L1 | L2 | L3 |
|------|----|----|-----|
| Host | 读写 | 读写 | 读写 |
| Knowledge Keeper | 读写（受Host委托） | 读写（受Host委托） | 读写（受Host委托） |
| Worker | 只读 | 只读 | 只读（可提交候选更新） |

---

## 四、片段级引用格式

为避免 token 浪费，知识库引用使用片段级定位：

```
格式：{层级}/{版本}#{章节标识符}

示例：
l1/current#tech-stack       → L1 当前版本 · 技术选型章节
l2/v2#api-protocol          → L2 v2 · API 协议章节
l3/latest#user-model-fields → L3 最新 · 用户模型字段
```

Worker 在回报中可附带候选更新：
```json
{
  "candidate_update": {
    "target": "l3/current#user-model-fields",
    "suggested_content": "新增字段: email_verified: boolean",
    "reason": "认证模块需要此字段"
  }
}
```

---

## 五、知识库裁决流程

```
Worker 提出候选更新
     ↓
Knowledge Keeper 初审（格式/冲突检查）
     ↓
Host 终审（架构影响评估）
     ↓
通过 → 写入知识库 / 驳回 → 通知 Worker 原因
```
