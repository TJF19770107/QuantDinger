# 龙虾-双层元Agent解冻协议 v1.0

> **协议编号**：#48
> **对标来源**：MetaAgent-X (俄勒冈州立大学+UCSD+宾州州立+AG2AI, arXiv:2605.14212)
> **创建日期**：2026-06-01 (R11)
> **核心价值**：设计者Agent和执行者Agent同时学习进步，打破"冻结"瓶颈，实现元层自改善
> **状态**：ACTIVE

---

## 一、协议概述

### 1.1 问题定义
现有自动多Agent系统中，"设计者Agent"（负责设计工作流/分配任务）在执行过程中是冻结的——它不会根据"执行者Agent"的表现来优化自己的设计策略。MetaAgent-X用一个餐厅比喻："总经理设计菜单、安排大厨分工后就下班了，不会根据顾客反馈调整菜单"。本协议打破这个"冻结"瓶颈，让设计者和执行者同时学习进步。

### 1.2 核心创新
- **双向反馈**：执行者向设计者反馈执行数据 → 设计者调整方案 → 执行者再优化
- **元层自改善**：设计者的设计策略随任务演化，不是写死的规则
- **协同进化**：设计者和执行者形成一个互相激励的进化闭环

## 二、双层架构

### 2.1 角色定义

```
┌─────────────────────────────────────┐
│          设计者Agent (Designer)        │
│  • 任务分析与拆解                      │
│  • 工作流设计                          │
│  • 子任务分配策略                      │
│  • 质量评审标准定义                     │
│  • 基于执行反馈自我改进                 │
└──────────────┬──────────────────────┘
               │ 任务分配
               ▼
┌─────────────────────────────────────┐
│        执行者Agent群 (Workers)         │
│  • Worker 1: 编码执行                 │
│  • Worker 2: 测试执行                 │
│  • Worker 3: 审查执行                 │
│  • 执行结果反馈至设计者                │
└─────────────────────────────────────┘
```

### 2.2 双向反馈协议

```json
{
  "feedback_type": "execution_result | strategy_feedback",
  "from": "worker_1",
  "to": "designer",
  "task_id": "task_abc",
  "metrics": {
    "success": true,
    "duration_ms": 2340,
    "errors": [],
    "quality_score": 0.92
  },
  "suggestions": [
    "子任务拆解粒度可更细",
    "Worker 2和Worker 3可并行"
  ]
}
```

## 三、元层自改善循环

### 3.1 三层进化

| 层级 | 进化对象 | 触发条件 | 示例 |
|------|---------|---------|------|
| L1 执行层 | 执行者策略 | 单任务失败 | 调整工具调用参数 |
| L2 设计层 | 设计者策略 | 同类任务连续低效 | 调整任务拆解粒度 |
| L3 元层 | 设计者元策略 | 多类任务均低效 | 调整拆解方法论 |

### 3.2 元策略示例
```
if 连续3个编码任务超过预估时间50%:
    设计者调整: 增加预分析阶段 + 缩小单任务范围

if 执行者间等待时间超过总时间20%:
    设计者调整: 重新分析依赖关系，增加并行度

if 同一执行者反复犯同一类错误:
    设计者调整: 为该执行者分配预检步骤
```

## 四、解冻机制

### 4.1 解冻时机
| 触发事件 | 解冻范围 |
|---------|---------|
| 单任务完成 | 该任务的设计策略反馈更新 |
| 同类任务批次完成（≥5个） | 该类的设计策略版本更新 |
| 跨类任务累计≥50个 | 元层策略全面复盘优化 |

### 4.2 安全约束
1. 设计者不可在任务执行中途修改已分配的子任务
2. 策略变更需版本化，支持回退
3. 解冻频率有上限（每小时≤3次策略更新）
4. 元层变更需经过Rubric自纠正（协议#26）
