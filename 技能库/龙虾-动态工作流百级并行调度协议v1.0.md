## 二、百级并行调度架构

### 2.1 调度拓扑

```
                     ┌──────────────────┐
                     │   Orchestrator   │
                     │   主编排Agent     │
                     │  编制整体计划      │
                     │  动态DAG分解      │
                     └──────┬───────────┘
                            │
              ┌─────────────┼─────────────┐
              │             │             │
         ┌────▼────┐  ┌────▼────┐  ┌────▼────┐
         │ 并行批1  │  │ 并行批2  │  │ 并行批3  │
         │ (30子A) │  │ (40子A) │  │ (30子A) │
         └────┬────┘  └────┬────┘  └────┬────┘
              │             │             │
              └─────────────┼─────────────┘
                            │
                     ┌──────▼───────────┐
                     │   Validator      │
                     │   统一校验输出     │
                     │   交叉验证        │
                     │   结果聚合        │
                     └──────────────────┘
```

### 2.2 三阶段执行流程

```
阶段一：Plan（计划编制）
  ├─ 任务语义分析
  ├─ DAG拓扑分解
  ├─ 依赖关系标注
  ├─ 并行度评估（确定批次数和每批子Agent数）
  └─ 资源预算分配

阶段二：Execute（并行执行）
  ├─ 批次1: N1个子Agent并行
  │   ├─ 子Agent独立上下文
  │   ├─ 共享只读文件系统
  │   └─ 中间结果写入共享存储
  ├─ 批次2: N2个子Agent并行（依赖批次1结果）
  │   └─ ...
  └─ 批次K: N_K个子Agent并行

阶段三：Validate（统一校验）
  ├─ 各子Agent输出收集
  ├─ 交叉验证（关键路径双Agent验证）
  ├─ 冲突检测与解决
  ├─ 结果聚合与汇总
  └─ 最终报告生成
```

### 2.3 并行度控制策略

| 参数 | 默认值 | 说明 |
|------|--------|------|
| max_parallel_agents | 100 | 单批最大并行子Agent数 |
| batch_size | 30 | 每批子Agent数（受上下文窗口限制） |
| min_batch_interval | 0.5s | 批次间最小间隔 |
| validation_ratio | 0.1 | 交叉验证比例（10%关键路径双验） |
| token_budget_per_agent | 50K | 每子Agent Token预算 |

## 三、动态工作流分支决策

### 3.1 多维条件分支

```
任务执行中动态决策节点：
├─ 执行结果质量评分 < 阈值 → 重新派发
├─ 子Agent超时 → 熔断 + 备用Agent接管
├─ 中间发现新依赖 → 动态扩展DAG
├─ 资源利用率 > 80% → 降并发 + 排队
└─ 用户中途介入 → 暂停 + 合并用户反馈
```

### 3.2 断点续传机制

| 场景 | 处理策略 |
|------|---------|
| 子Agent崩溃 | 检查点恢复，从最后成功步骤继续 |
| 批处理中断 | 已完成批次结果持久化，重启后跳过 |
| 上下文溢出 | 中间结果卸载至外部存储，仅保留摘要 |
| Token预算耗尽 | 优雅降级，简化后续子Agent任务描述 |

## 四、Fast Mode成本优化

### 4.1 三档速度模式

| 模式 | 速度 | 适用场景 | 成本系数 |
|------|------|---------|---------|
| Standard | 基准 | 复杂推理、代码生成、安全审查 | 1× |
| Fast | 2.5× | 实时交互、批量处理、简单查询 | 0.33×(降价3倍) |
| Turbo | 5×+ | 大规模并行、流式响应 | 按API定价 |

### 4.2 动态模式切换

```
任务复杂度评估 → 模式选择：
├─ 简单（单步查询/文件列表） → Fast Mode
├─ 中等（多步操作/数据分析） → Standard Mode
├─ 复杂（编码/推理/安全审查） → High Effort Mode
└─ 超复杂（架构设计/迁移） → Max Effort + Dynamic Workflows
```

### 4.3 Effort Control滑块映射

| 档位 | 思考深度 | Token消耗 | 适用任务 |
|------|---------|----------|---------|
| standard | 浅 | 低 | 简单对话、快速查询 |
| high (默认) | 中 | 中 | 一般编码、文档处理 |
| xhigh | 深 | 高 | 复杂bug修复、架构分析 |
| max | 极深 | 极高 | 安全审计、关键系统重构 |

### 5.2 新增能力：超越单一上下文窗口

```
传统模式：
  任务 → 单次上下文窗口处理 → 结果
  限制：窗口内装不下的任务无法处理

Dynamic Workflows模式：
  任务 → DAG分解 → 批次1（窗口1）→ 批次2（窗口2）→ ...
        └─ 中间结果持久化到外部存储
        └─ 仅关键摘要跨窗口传递
        └─ 最终聚合超越窗口限制
```

### 5.3 代码诚实性提升

基于Claude Opus 4.8代码诚实性4×提升，豆包Agent应：
- 主动标注输出中的不确定性
- 静默错误放过减少4倍
- 在Code Review场景中优先使用High Effort模式
- 关键代码路径自动追加追问验证
