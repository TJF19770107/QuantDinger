## 一、全网深度检索成果

### 1.1 多Agent架构协议层 —— A2A v1.2 标准化

| 维度 | 核心发现 |
|------|----------|
| **协议归属** | Google 2025.4 发布 → 2025.6 捐赠 Linux Foundation → 2026年初 v1.0 生产可用 → 2026.3 v1.2 发布 |
| **生态规模** | 150+ 组织支持，多个行业进入生产部署 |
| **核心数据模型** | Agent Card（能力名片）、Task（有状态任务）、Message（通信载体）、Artifact（产出物） |
| **交互模式** | 同步请求/响应、异步轮询、SSE流式推送、Push Notification回调 |
| **与MCP关系** | 互补非竞争：MCP = Agent↔Tool（USB接口），A2A = Agent↔Agent（HTTP协议） |

**A2A Task生命周期状态机**：
```
submitted → working → completed / failed / input-required
         → canceled（任意时刻）
         → rejected（服务端拒绝）
```

**关键洞察**：2026年主流多Agent架构已形成 **MCP + A2A 双层模型**。MCP解决工具调用，A2A解决Agent协作委托。这与Marvis的1+5架构高度契合——Marvis内部使用专有调度协议（结构化任务描述+memory_ids+inherit_agent_id），外部对接可考虑A2A标准化。

### 1.3 Hermes Agent —— 自进化Agent标杆

| 维度 | 详情 |
|------|------|
| **开发者** | Nous Research |
| **首次发布** | 2026.02 v0.1.0 |
| **GitHub增长** | 42天获47K Stars（GitHub史上增速最快Agent项目） |
| **核心创新** | Learning Loop 学习闭环：经验→技能→自我优化 |
| **最新版本** | v2.1 SWARM（2026.5.3） |

**Hermes v2.1 SWARM 多Agent编排**：
```
Orchestrator（中央调度）
  ├── Agent A：调研和资料收集
  ├── Agent B：撰写初稿
  ├── Agent C：审核和润色
  └── Agent D：排版和发布
  
+ Kanban TaskBoard（看板式任务管理）
+ Reports + Inbox（结果汇总与通知）
```

**三层记忆架构**：
1. Working Memory → Episodic Memory → Semantic Memory
2. Procedural Memory（Skills）
3. FTC5全文搜索 + LLM摘要总结 + Honcho辩证用户建模

**九种协作模式**：扇出并行、流水线、投票仲裁、人在环中审核等

**启示**：Hermes的Learning Loop机制是当前自进化Agent的最高水准参考。其"从经验中提炼技能、技能在使用中自优化"的闭环，可直接对标我们的AgentIter + KBArchiving技能组合。

### 1.4 Marvis 1+5 架构 —— 操作系统的AI中间层

| 角色 | Agent | 定位 |
|------|-------|------|
| 大脑 | 主Agent（PM Agent） | 意图理解、任务拆解、调度汇总 |
| 手1 | File Agent | 本地文件全生命周期 |
| 手2 | Computer Agent | Windows系统运维与底层操控 |
| 手3 | App Agent | 桌面软件+安卓应用操作 |
| 手4 | Browser Agent | 网页深度交互与数据抓取 |
| 手5 | Search Agent | 全网信息检索与摘要整理 |

**核心通讯机制**：
- **星型拓扑**：专项Agent不直接通讯，全部经主Agent中转
- **结构化任务描述**：`<overall_goal>` + `<current_task>` + memory_ids + inherit_agent_id
- **能力层级路由**：Sub Agents → Skills → Tools → 生成代码执行
- **依赖感知调度**：无依赖并行、有依赖串行，单轮最多5并行
- **端云双模式**：复杂意图云端推理，简单操作本地执行

**安全校验**：三级风险定级（高/中/低），贯穿全链路

## 二、全域能力融合分析

### 2.1 能力对标矩阵

| 能力维度 | 龙虾当前 | Hermes Agent | OpenClaw | Marvis | 差距评估 |
|----------|----------|-------------|----------|--------|----------|
| 多Agent调度 | AgentIter（批量迭代） | SWARM Orchestrator（中央调度+看板） | 单进程执行 | 1+5星型拓扑 | 缺看板式任务管理与自动认领 |
| 自进化闭环 | KBArchiving（学习沉淀） | Learning Loop（自动技能提取） | 无 | 无 | 缺自动技能生成机制 |
| 跨平台接入 | 12技能本地化 | 20+消息平台网关 | 插件体系 | 端云双模式 | 平台网关数量不足 |
| 记忆管理 | MemoryMgr（同步修复） | 三层记忆架构（FTC5+摘要+建模） | 会话级 | 长上下文 | 缺辩证用户建模层 |
| 异常处理 | ECCFramework（3次重试） | Kanban熔断机制（3次失败锁定） | 无 | 安全校验层 | 机制相似，缺看板级熔断 |
| 任务调度 | ScheduledOps（定时运维） | 内置Cron调度器 | 无 | 定时任务 | 功能对齐 |
| 知识库联动 | KBArchiving（归档去重） | 技能文件系统 | 无 | 本地文件系统 | 深度联动Obsidian已领先 |

### 2.2 核心短板识别

1. **缺SWARM级多Agent协同调度**：当前AgentIter仅支持批量迭代，缺乏中央Orchestrator + Kanban TaskBoard + Worker自动认领机制
2. **缺Learning Loop自动技能生成**：KBArchiving需手动触发，无法像Hermes那样从经验中自动提取Skill
3. **缺20+平台消息网关**：仅通过Marvis渠道通信，无法接入Telegram/Discord/飞书/钉钉等外部平台
4. **缺辩证用户建模**：MemoryMgr仅做同步修复，未建立用户行为模型

### 2.3 对标升级路径

```
当前架构                          目标架构（融合Hermes+Marvis+OpenClaw）
─────────                        ─────────────────────────────────
AgentIter（批量迭代）     →      SWARM Orchestrator（中央调度+看板+自动认领）
KBArchiving（手动归档）   →      Learning Loop（自动技能提取+自我优化）
12技能本地化              →      12技能 + 多平台网关接入
MemoryMgr（同步修复）      →      三层记忆（全文搜索+摘要+用户建模）
ECCFramework（3次重试）    →      Kanban熔断（3次失败→锁定→人工介入）
```
