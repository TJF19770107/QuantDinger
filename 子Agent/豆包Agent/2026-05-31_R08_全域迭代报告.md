### 1.2 本轮重点情报解读

#### 情报 A：Anthropic Claude Opus 4.8 + 动态工作流

Anthropic以9650亿美元估值完成650亿美元H轮融资，同步发布Claude Opus 4.8。关键升级点：
- **动态工作流**：Claude Code不再遵循固定步骤，而是根据任务上下文动态调整执行路径
- **多Agent协作增强**：子Agent间共享文件系统，事件记忆机制
- **年化收入超470亿美元**：商业模式已验证

**对豆包的启示**：当前工作流偏线性（五步法），可引入动态分支决策节点。

#### 情报 B：OpenAI Codex Computer Use 登陆 Windows

Codex 26.5.27版本核心能力：
- **屏幕识别**：理解屏幕内容，定位UI元素
- **键鼠控制**：模拟鼠标点击、键盘输入
- **远程控制**：手机端操控电脑任务
- **前台运行限制**：当前版本需前台执行

**对豆包的启示**：桌面控制需对标屏幕视觉理解能力，从"命令调用"升级到"视觉操控"。

#### 情报 C：GenericAgent 极简自进化框架

核心理念：**"don't preload skills — evolve them"**

| 特性 | GenericAgent | 豆包当前 |
|------|-------------|---------|
| 核心代码量 | ~3,000行 | 技能协议30项 |
| 原子工具 | 9个 | 多个专用工具 |
| 技能获取 | 自主生长 | 协议固化和提取 |
| Token效率 | 6倍更少 | 30项协议全量加载 |
| 记忆系统 | 5层分层 | MemoryOS v2.0 |

**核心差异**：GenericAgent强调极简原子工具 + 自主进化Skill，而非预设大量技能协议。豆包已有30项技能协议，需反思"协议膨胀"风险。

#### 情报 D：Hermes 多Agent编排者-工作者模式

关键技术要素：
- **结构化结果对象**：Worker不传摘要，传typed result object，编排者直接合成
- **四种通信模式**：Fan-out/Fan-in、Pipeline、Validator loop、竞争模式
- **模型分离**：编排者用便宜快速模型，Worker用强推理模型
- **PLUR插件**：跨Agent经验共享

**对豆包的启示**：当前多Agent协同看板（协议1）偏SQLite原子认领，可引入结构化结果传递层。

#### 情报 E：阿里Qoder Quest 1.0 自进化范式

- **Spec驱动**：复杂工程先生成技术规约，再编码
- **多子Agent并行探索**：不同实现路径并行，择优而行
- **自修复闭环**：诊断根因→生成修复→验证效果，全自动

#### 情报 F：Marvis 正式上线（豆包对标参考）

Marvis核心能力矩阵（对标参考）：

### 3.2 重点协议设计摘要

#### 协议31：极简原子工具自进化协议 v1.0

**问题**：当前30项技能协议日趋膨胀，Token消耗上升，部分协议使用率低。
**方案**：借鉴GenericAgent哲学，定义不超过10个原子工具作为"种子能力"，其余能力全部通过自进化生长。

```
种子工具集（≤10个）：code_run / file_read / file_write / file_patch / 
                      web_scan / web_execute / ask_user / shell_exec / 
                      dispatch_task / memory_inject
```

五层分层记忆路由：
```
L0 — 元规则（不可变，如安全约束）
L1 — 记忆索引（快速路由表，按任务类型分桶）
L2 — 全局事实（长期稳定的领域知识）
L3 — 任务Skills/SOPs（可复用流程，自进化生长）
L4 — 会话归档（长程召回，按相关性衰减）
```

每次任务结束，自动将新发现的执行路径固化为L3 Skill。同类任务下次直接调用，跳过摸索阶段。

#### 协议32：编排者-工作者结构化结果协议 v1.0

**问题**：当前多Agent协同看板（协议1）使用SQLite原子认领，子Agent间信息传递靠摘要，存在信息衰减。
**方案**：引入Hermes式结构化结果对象传递。

```
通信模式：
- Fan-out/Fan-in：编排者并行派发多Worker，等待全部结果后合成
- Pipeline：Worker输出直接作为下一个Worker输入
- Validator loop：专用验证者检查Worker输出，不合格打回修改
- 竞争模式：多Worker并行探索不同路径，择优采用
```

模型分层策略：编排者用快速便宜模型（仅做任务拆解和结果路由），Worker用强推理模型（实际执行）。

#### 协议33：视觉桌面操控协议 v1.0

**问题**：当前桌面控制依赖系统API和坐标定位，无法处理动态UI变化。
**方案**：引入Codex Computer Use的屏幕视觉理解能力。

```
三层操控架构：
L1 — 屏幕理解：截图→视觉模型识别UI元素→定位操作目标
L2 — 键鼠模拟：基于视觉定位生成精确的点击/拖拽/输入动作
L3 — 远程接管：手机端实时可视化操控电脑桌面
```
