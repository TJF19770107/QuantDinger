## 一、协议目标

将SICA论文的"完全自指元Agent编程"架构融入豆包Agent的自进化核心闭环，消除传统"元Agent→目标Agent"的二分界限，实现Agent直接编辑自身代码库的自主进化。升级现有的SICA增强反馈循环为完全自指架构。

---

## 二、核心突破：消除元Agent与目标Agent的界限

### 2.1 传统架构 vs 完全自指架构

```
传统（ADAS / 现有SICA v2.0）:
  元Agent ──(分析/修改)──→ 目标Agent
     ↑                        │
     └──────(评估反馈)────────┘
  → 分离的两个实体，元Agent不改自身

完全自指（SICA v3.0 / R07）:
  Agent ──(基准测试)──→ Agent ──(分析反思)──→ Agent
    ↑                                              │
    └──────────(代码重写自身)──────────────────────┘
  → 同一个Agent既是执行者也是改进者
```

### 2.2 关键区别

| 维度 | v2.0 SICA | v3.0 完全自指 |
|------|----------|-------------|
| 改进主体 | 独立元Agent | Agent自身 |
| 改进对象 | 目标Agent代码库 | 自身代码库 |
| 评估循环 | 元→目标→元 | 自→自→自 |
| 复利效应 | 线性 | 指数（改进能力随自身升级增强） |
| 适用边界 | 工具/流程 | 工具/流程（不含核心推理） |

## 三、四步自进化循环

```
┌──────────────────────────────────────────────────────┐
│              完全自指进化循环 (SICA v3.0)               │
│                                                      │
│  Step 1: 基准测试 (Benchmark)                        │
│    在预设任务集上测试当前版本性能                       │
│    记录：通 过率 / 耗时 / Token消耗 / 错误类型分布       │
│         │                                            │
│         ▼                                            │
│  Step 2: 分析反思 (Analyze & Reflect)                │
│    表现最佳版本作为"元Agent"，分析测试结果              │
│    识别：瓶颈点 / 可优化路径 / 重复失败模式             │
│    输出：改进方案（修改哪些文件/新增什么能力）           │
│         │                                            │
│         ▼                                            │
│  Step 3: 代码重写 (Rewrite)                          │
│    直接编辑自身代码库：创建新工具/优化流程/重构模块       │
│    生成Diff → SafeGuard审查 → 通过后写入               │
│    异步监察者旁路监控，防止跑偏                         │
│         │                                            │
│         ▼                                            │
│  Step 4: 循环迭代 (Iterate)                          │
│    新版本进入下一轮基准测试                             │
│    对比上一版本：效用函数(性能+成本+时间)是否提升         │
│    若提升 → 新版本成为下一代基线                        │
│    若退化 → 自动回滚 + 记录退化原因                     │
└──────────────────────────────────────────────────────┘
```

## 四、效用函数引导进化

### 4.1 三维效用函数

```
U = α·P + β·(1/C) + γ·(1/T)

其中:
  P = 性能得分（任务通过率 × 质量加权）
  C = 归一化Token成本（越低越好）
  T = 归一化执行时间（越低越好）
  α, β, γ = 权重系数（可配置，默认 α=0.5, β=0.3, γ=0.2）
```

### 4.2 效用函数的作用

- 防止Agent为追求性能不惜成本（无限重试/无限Token）
- 防止Agent为降低成本牺牲质量
- 多目标Pareto优化：不追求单一极值

## 五、已知边界（关键教训）

### 5.1 纯推理任务无效

SICA论文明确结论：在AIME数学竞赛和GPQA高难度问答上，自改进框架**无效**。

**原因**：外部Scaffolding打断模型内在推理连贯性。对于依赖连贯思维链的纯推理任务，代码层面的自改进是干扰而非辅助。

### 5.2 应用边界定义

| 任务类型 | 完全自指有效？ | 建议 |
|---------|-------------|------|
| 软件工程/编码 | ✅ 极高 | 核心应用场景 |
| 工具/流程优化 | ✅ 高 | 工具链自改进 |
| 多Agent编排 | ✅ 中 | 编排策略自调优 |
| UI自动化 | ✅ 中 | 操作序列优化 |
| 数学推理 | ❌ 无效 | 依赖模型升级 |
| 逻辑推理 | ❌ 无效 | 依赖模型升级 |
| 创意写作 | ⚠️ 边际 | 仅格式/结构优化有效 |

## 六、与异步监察者联动

完全自指意味着Agent拥有修改自身的能力，必须有独立监察层：

```
Agent执行自进化 ──→ 异步监察者独立监控
                        │
                ┌───────┴───────┐
                │               │
           行为正常          行为异常
                │               │
                ▼               ▼
           继续进化        提醒 → 建议纠正 → 强制取消
                                    │
                              自动回滚至上一稳定版本
```

详见 `龙虾-异步监察者安全协议v1.0.md`
