## 三、失败根因分析

### 3.1 第2轮失败详情

| 维度 | 描述 |
|------|------|
| **失败类型** | RemoteProtocolError — 连接断开 |
| **直接原因** | 阶段二全量读取任务过重，单次dispatch_task承载内容体积超限 |
| **任务特征** | 要求一次性读取技能库中全部.md文件全文，预估总行数>2000行 |
| **触发条件** | 单次任务上下文 + 返回结果 > 调度通道承载上限 |

### 3.2 瓶颈定位

```
调度通道容量瓶颈
├── 表现：全量读取任务触发连接断开
├── 根因：缺少自动拆分机制，任务粒度完全依赖人工定义
├── 影响：大体积任务不可靠，需人工介入重试/拆分
└── 严重度：中等（通过拆分可规避，但需告警机制）
```

## 四、优化建议

### 4.1 自动拆分阈值

| 参数 | 建议值 | 说明 |
|------|:---:|------|
| 单次任务最大文件数 | 6 个 | 超过则自动拆分为多个子任务 |
| 单次任务预估行数上限 | **< 200 行** | 按文件名+行数估算后触发拆分 |
| 子任务串行间隔 | 3 秒 | 避免调度通道拥塞 |

### 4.2 子任务体积限制策略

```
dispatch_task 执行前自动检查：
   if estimated_output_lines > 200:
       自动拆分为 N 个子任务
       N = ceil(estimated_output_lines / 200)
       按文件为单位分配，不拆分单文件
   else:
       正常执行
```

### 4.3 失败重试策略增强

| 场景 | 当前行为 | 建议增强 |
|------|---------|---------|
| RemoteProtocolError | 人工重试 | 自动捕获 + 降级拆分 + 重试 |
| 超时 | 人工重试 | 自动重试1次 → 仍失败则拆分 |
| 部分成功 | 仅日志 | 续传机制：已完成部分不重复 |

### 4.4 调度监控建议

- 引入每轮任务**预估体积 vs 实际体积**偏离度告警
- 连续2轮异常时自动触发降级协议（限制单次200行）
- 建立 Agent 成功率看板，低于70%的Agent自动标记为"需调优"

## 五、结论

本轮5次调度整体可用性 **80%**，核心瓶颈为**单次任务体积超限导致连接断开**。通过引入自动拆分阈值（<200行）和失败重试降级策略，可将预期成功率提升至 95%+。阶段一和阶段三的100%成功率验证了轻量任务在现有调度通道下运行稳定。
