## 二、七大对标目标深度分析

### 2.1 OpenAI Codex (GPT-5.2-Codex)

**当前状态**：2026 年已从独立编码模型进化为 GPT-5 家族的内置专门化能力。

**核心技术栈**：
- **Code Interpreter 闭环**：Write → Run → Debug 自我修复循环
- **Codex CLI**：开源的终端 Agent，直接操作本地仓库
- **MCP 集成**：CLI 可作为 MCP Server 运行，被 Agents SDK 编排
- **AGENTS.md / MCP**：仓库级适配与第三方工具扩展
- **沙箱 + 审批模式**：Human-in-the-Loop 安全保障

**豆包可借鉴**：
1. `Write → Execute → Trace → Fix` 闭环（目前豆包缺少 Execute 验证环节）
2. AGENTS.md 等效机制：项目级配置描述文件
3. 审批模式：关键操作前的用户确认流程

---

### 2.2 Claude (Anthropic)

**当前状态**：MCP 协议已成为行业标准，被 OpenAI、Google、Microsoft、AWS 全数采纳。

**核心技术栈**：
- **MCP 协议**：Client-Server 架构，三大原语 Tools / Resources / Prompts
- **Computer Use**：视觉+操作的系统级交互
- **Constitutional AI + CoT**：工具调用前先阐述推理逻辑
- **Tool Use 精确 JSON Schema 遵循**

**豆包可借鉴**：
1. **全面拥抱 MCP**：这是最高优先级的架构演进方向
2. **工具调用前 CoT**：减少盲目调用，提升工具使用效率
3. **Computer Use 能力**：为豆包增加屏幕视觉理解 + 鼠标键盘操作

---

### 2.3 Nous Hermes (中枢调度)

**当前状态**：代表多 Agent 协同的最高实践水平。

**核心技术栈**：
- **中枢调度器 (Manager Agent)**：接收任务 → 分解 → 分发给 Worker Agents
- **共享黑板机制**：消息队列 + 共享内存，减少 Agent 间通信噪音
- **树状 Agent 组织**：Hierarchical Agent Teams
- **Function Calling 微调**：严格 JSON Schema 遵循的专用数据集

**豆包可借鉴**：
1. 当前 Main Agent → Sub Agents 结构已是 Hierarchical 雏形
2. 需要增强 Sub Agent 间的直接协同（目前是串行派发）
3. 引入共享黑板概念：Agent 间可读写的共享状态池

---

### 2.4 OpenClaw (多模型路由网关)

**当前状态**：代表"Right Model for the Right Task"理念的实现。

**核心技术栈**：
- **智能路由**：简单任务→轻量模型，复杂任务→重型模型
- **统一网关**：抽象不同 LLM Provider 的 API 差异
- **Fallback & Redundancy**：主力模型宕机自动切换备用
- **Cost-Aware Routing**：基于 Token 成本的动态路由
- **Semantic Caching**：相似 Prompt 结果缓存

**豆包可借鉴**：
1. 豆包当前是单一模型执行，未来可引入多模型路由层
2. 为不同子任务选择最优模型（代码→Codex，分析→Claude，搜索→Gemini）
3. Semantic Caching 减少重复调用成本

---

### 2.5 OpenCode / Aider / Cline (AI IDE 工作流)

**当前状态**：2026 年开源 AI 编程工具已形成四大阵列。

**四大阵列分类**：

| 阵列 | 代表项目 | 核心特征 |
|------|---------|---------|
| 终端原生智能体 | Aider, Codex CLI, OpenCode | Git 深度集成，直接操作文件系统 |
| IDE 扩展插件 | Cline, Roo Code, Continue | 无缝嵌入 VS Code / JetBrains |
| AI 原生 IDE 分叉 | Void, PearAI, Melty | 深度修改编辑器底层 |
| 复杂工程编排平台 | OpenHands, Plandex | 长程规划 + 沙盒执行 |

**关键技术**：
- **Repo Map (Aider)**：用 ctags/tree-sitter 生成代码库拓扑图
- **Diff Editing**：生成 Search/Replace 块而不是全量代码
- **LSP 集成 (OpenCode)**：语言服务器协议，代码导航与诊断
- **Auto Compact (OpenCode)**：实时监测 Token 消耗，自动摘要对话
- **TDD Agent**：先写测试 → 再写代码 → 验证

**豆包可借鉴**：
1. **Diff-based Editing**：用 Search/Replace 替代全量代码生成（降低错误率）
2. **Repo Map**：静态分析生成代码结构索引，减少上下文浪费
3. **Auto Compact**：对话超长时自动压缩，保持任务连贯性
4. **LSP 集成**：实时代码诊断反馈

---

### 2.6 Google Gemini

**当前状态**：1M Token 上下文窗口 + 多模态推理。

**核心技术栈**：
- **1M Token Context**：整个中型代码库一次性塞入 Prompt
- **多模态推理**：原生视频/音频理解，录屏 Bug 演示直接定位代码
- **Needle-in-a-Haystack**：长文本精确定位替代传统向量检索
- **System Instructions**：精确控制模型角色和行为

**豆包可借鉴**：
1. 长上下文策略：当 token 预算充裕时，采用全量加载替代 RAG 切片
2. 多模态输入：支持截图/录屏作为 Bug 报告的直接输入
3. System Instructions 分层：全局指令 vs 任务级指令隔离

---

### 2.7 Marvis Workbody（工作体架构）

**当前状态**：代表有状态执行 + 长期记忆 + 工具具身的 Agent 架构。

**核心技术栈**：
- **Stateful Execution**：向量数据库存储项目文档与个人偏好
- **Workbody 概念**：Agent 拥有"身体"（API 权限、文件访问、浏览器控制）
- **RPA + LLM 结合**：确定性操作用 RPA 脚本，非结构化决策用 LLM
- **Human-in-the-Loop**：关键决策点强制暂停等待确认

**豆包可借鉴**：
1. 豆包已具备 Workbody 雏形（文件系统、Sub Agent 工具调用）
2. 需要增强：长期项目记忆（跨会话的代码库理解）
3. 需要增强：关键操作前的 HITL 确认（已有安全框架，可继续强化）
