## 一、Building Effective Agents（Anthropic 官方原文精要）

**原文**：https://www.anthropic.com/engineering/building-effective-agents

### 1.1 核心定义：Agent vs Workflow

Anthropic 将所有变体归类为 **代理化系统（Agentic Systems）**，并做了重要架构区分：

| 类型 | 定义 | 控制方式 |
|------|------|----------|
| **Workflow（工作流）** | LLM 和工具通过预定义代码路径编排 | 人类定义路径 |
| **Agent（智能体）** | LLM 动态指导自身流程和工具使用 | AI 定义路径 |

> **核心主张**：从最简单的方案开始，只在必要时增加 Agent 的自主性。Workflow 解决 80% 的问题，Agent 只用于剩余 20%。

### 1.2 五种核心模式

#### 模式一：Prompt Chaining（提示链）
- **结构**：任务分解为顺序步骤，每个 LLM 调用处理前一个的输出
- **适用**：营销文案生成→翻译、写大纲→检查大纲→写正文
- **价值**：用延迟换准确率

#### 模式二：Routing（路由）
- **结构**：输入分类→分发到专门的下游处理流程
- **适用**：客服分类分流、简单问题用小模型/复杂问题用大模型
- **价值**：成本优化与专业化分工

#### 模式三：Parallelization（并行化）
- **Sectioning**：任务分解，并行执行后聚合（一个模型处理查询，另一个审核内容）
- **Voting**：相同任务多次执行，投票输出（多角度代码审查）
- **价值**：速度提升 + 准确性增强

#### 模式四：Orchestrator-Workers（编排器-工作者）
- **结构**：一个中央 LLM 协调多个“工人”LLM 执行子任务
- **适用**：编码任务中分别处理编写代码、测试和调试
- **价值**：复杂任务分解与并行执行

#### 模式五：Evaluator-Optimizer（评估器-优化器）
- **结构**：评估器评估输出→优化器根据反馈改进→迭代循环
- **适用**：文学翻译、复杂搜索任务
- **价值**：追求高精度的迭代优化

### 1.3 四大设计原则

1. **简单性**：从最简单的解决方案开始，只在必要时增加复杂性
2. **透明度**：让 Agent 的决策过程可见，展示规划步骤
3. **良好的 ACI 设计**：通过工具文档和测试确保易用性，清晰工具定义减少错误
4. **生产环境优化**：减少框架抽象，保持对系统的控制和理解

### 1.4 何时使用 Agent 的决策框架

```
是否需要 Agent？
├─ 单次 LLM 调用 + 检索/上下文示例 够用？
│   └─ YES → 不要用 Agent
├─ 任务有明确边界和预定义步骤？
│   └─ YES → 用 Workflow
└─ 任务需要灵活性 + 模型驱动决策？
    └─ YES → 用 Agent
```

## 二、Claude Code 子代理（Subagents）体系

**原文**：How and when to use subagents in Claude Code（2026年4月7日）

### 2.1 子代理核心概念

子代理（Subagent）是拥有**独立上下文窗口**的自包含代理实例。完成后仅将精简结果返回主对话。

**三大核心特性**：

| 特性 | 说明 | 优势 |
|------|------|------|
| 独立上下文 | 全新的上下文窗口 | 不受主对话历史负担 |
| 并行执行 | 多个子代理可并发运行 | 多任务并行=更短完成时间 |
| 差异化权限 | 每个子代理可有不同工具权限 | 研究代理只读，实现代理可编辑 |

### 2.2 三种内置子代理类型

| 类型 | 模型 | 权限 | 适用场景 |
|------|------|------|----------|
| **Explore** | Haiku | 只读 | 文件发现、代码搜索、调用链分析 |
| **Plan** | 继承主模型 | 只读 | 大型重构前调研、上下文收集 |
| **General-purpose** | 继承主模型 | 全部工具 | 重构、新功能实现、复杂多步任务 |

### 2.3 五种触发方式（渐进式自动化路径）

```
1. 对话式调用（临时）
   ↓ 观察哪些请求反复出现
2. 自定义子代理（固化到 .claude/agents/）
   ↓ 模式成熟后
3. CLAUDE.md 指令（团队规范）
   ↓ 确定必须强制执行时
4. 技能 Skills（按需加载的可复用工作流）
   ↓
5. 挂钩 Hooks（生命周期自动触发）
```

### 2.4 自定义子代理设计要素

```yaml
---
name: security-reviewer
description: 触发条件应明确（如"before commits touching auth, payments"）
tools: Read, Grep, Glob  # 最小权限原则
model: sonnet
---
# 系统提示词结构：
# 1. 明确目标（"查找所有 SQL 注入风险"而非"检查代码"）
# 2. 指定范围（"只看 src/api/ 目录"）
# 3. 定义输出（"返回问题列表+修复建议"）
# 4. 设定约束（"只读分析，不修改文件"）
# 5. 兜底行为（"未发现问题时明确说明，不编造"）
```

### 2.5 四大实用工作模式

| 模式 | 场景 | 关键机制 |
|------|------|----------|
| 实施前研究 | 动手前充分了解现有代码 | 子代理探索→返回提炼发现 |
| 并行修改 | 多个文件应用相同模式 | 多个子代理同时修改不同文件 |
| 独立审查 | 不受之前对话影响的客观审查 | 全新上下文=真正"第二意见" |
| 管道工作流 | 具有清晰交接的顺序阶段 | 输出文件作为阶段间交接物 |

### 2.6 权限管理策略

| 代理类型 | 建议权限 | 原则 |
|----------|----------|------|
| 研究/探索代理 | Read, Grep, Glob | 只读 |
| 代码审查代理 | Read, Grep, Glob | 只读 |
| 实现代理 | Read, Write, Bash, Grep, Glob | 按需 |
| 测试运行代理 | Read, Bash | 可执行测试但不能编辑 |

### 2.7 常见陷阱与规避

| 陷阱 | 症状 | 规避方法 |
|------|------|----------|
| 上下文浪费 | 子代理返回大量原始内容 | 要求"返回摘要而非原始内容" |
| 并行冲突 | 多个子代理修改同一文件 | 确保并行任务操作不同文件 |
| 代理泛滥 | 自动委派不可靠 | 限制自定义代理数量（5-8个） |
| 过度委派 | 简单任务也用子代理 | 只在10+文件或3+独立任务时启用 |
| 权限过松 | 审查代理意外修改代码 | 严格配置tools白名单 |

### 2.8 速查决策树

```
需要探索 10+ 文件？→ 使用子代理
涉及 3+ 独立任务？→ 使用子代理
需要无偏见审查？→ 使用子代理
临时使用？→ 对话式调用
反复使用？→ 自定义代理（.claude/agents/）
团队规范？→ CLAUDE.md / Skills
必须执行？→ Hooks（生命周期自动触发）
只读场景？→ Read/Grep/Glob
编辑场景？→ 加上 Write/Bash
耗时任务？→ Ctrl+B 后台
```

## 三、Agent Teams 多Agent协作体系

### 3.1 核心概念分层

```
┌─────────────────────────────────┐
│         Agent Teams（协作层）      │
│  多会话并行、互相通信、任务协调      │
├─────────────────────────────────┤
│       Subagents（执行层）          │
│  独立上下文、并行执行、权限差异化     │
├─────────────────────────────────┤
│     Skills（知识层）              │
│  可复用工作流、按需加载             │
├─────────────────────────────────┤
│    MCP Servers（连接层）          │
│  外部数据库、API、工具连接          │
└─────────────────────────────────┘
```

**一句话总结**：Skills 教会 Agent 怎么做，MCP 让 Agent 能连接外部世界，子代理负责并行干活，Agent Teams 让多个代理之间能协商。

### 3.2 Claude Code 四大组件

| 组件 | 角色 | 类比 |
|------|------|------|
| 子代理（Subagents） | 干活的工人 | 外包的自由职业者 |
| Agent Teams | 协作的团队 | 能互相沟通的项目组 |
| Skills | 专业知识库 | 工人手里的操作手册 |
| MCP Servers | 外部连接器 | 通往数据库/API/工具的桥梁 |

### 3.3 Agent Teams 最佳实践

1. **明确文件边界，避免冲突**：按文件/目录划分（src/frontend/、src/backend/api/），不要按功能划分
2. **团队规模控制在 3-5 人**：超过 5 个队友协调开销超过并行收益
3. **先做研究任务，再做并行实现**：1个队友做全面分析→团队领导制定统一接口→4个队友并行实现
4. **使用 Hooks 强制质量门**：TeammateIdle 时自动验证输出

### 3.4 任务管理系统

Claude Code 内置 Tasks API：
- 状态流转：pending → in_progress → completed
- 依赖关系：blockedBy / blocks
- Ctrl+T 切换任务列表显示
- CLAUDE_CODE_TASK_LIST_ID 跨 session 共享任务列表

## 四、Agentic Engineering 工程化实践

### 4.1 从 Vibe Coding 到 Agentic Engineering

| 阶段 | 特征 | 时间 |
|------|------|------|
| Vibe Coding | 完全交给AI，不看diff | 2025.02 |
| Agentic Engineering | 99%时间在协调agent | 2026.02 |

**核心转变**：从"AI 写代码真酷"到"如何系统性地用 AI agent 做工程"

### 4.2 Agentic Engineering 核心原则（Simon Willison）

1. **能干活再谈抽象**：先用最直接的方式让 Agent 完成任务
2. **上下文即工程**：CLAUDE.md 是所有 Agent 共享的上下文基础
3. **可复用资产**：Skills、Subagent 配置应团队共享、版本管理
4. **失败模式记录**：记录 Agent 出错的模式，建立避坑指南

### 4.3 实用技能清单

| 技能 | 用途 | 关键词 |
|------|------|--------|
| brainstorming | 创意工作前强制探索需求 | 创意/设计/功能 |
| summarize | URL/视频/播客/PDF 摘要 | 摘要/转录 |
| doc-coauthoring | 结构化文档协作 | 文档/提案/技术规范 |
| frontend-design | 生产级前端界面 | 网页/组件/UI |
| frontend-slides | HTML演示文稿 | PPT/slides/演讲 |
| brand-guidelines | Anthropic品牌风格 | 品牌/视觉/风格 |
| canvas-design | 海报/设计/艺术 | 海报/设计 |
| skill-creator | 创建新技能 | 创建技能 |
| skill-vetter | 安全检查 | 技能审查 |

### 4.4 MCP 服务器生态

| 服务器 | 功能 | 类型 |
|--------|------|------|
| filesystem | 文件系统操作 | 安全读写 |
| github | GitHub API | 仓库管理 |
| postgres | 数据库查询 | 只读/读写 |
| slack | 消息通知 | 通信 |
| playwright | 浏览器自动化 | 网页交互 |
| memory | 知识图谱 | 持久化记忆 |

### 4.5 核心工作流参考

**标准开发工作流**：
```
/brainstorm → Plan Mode → /todo-write → 实现 → /review → 提交
```

**Agent Teams 工作流**：
```
/brainstorm → 1个Agent做全面分析 → 团队领导整合+制定规范 → 多个Agent并行实现 → Hooks自动验证
```

## 五、Computer Use & Agent SDK 进阶

### 5.1 Computer Use（2024.10）

- Agent 直接操作计算机：移动鼠标、点击、键入、截图
- 适用：无法通过 API 访问的传统软件自动化
- 原则：最小权限、沙箱隔离

### 5.2 Agent SDK（2025.09）

- 官方 SDK 简化 Agent 构建
- 支持 Workflow 和 Agent 两种模式
- 内置工具管理、记忆系统、安全护栏

### 5.3 Constitutional AI 2.0

- 用宪法原则做 RLAIF（AI反馈强化学习）
- 从人类反馈转向原则驱动的自主对齐
