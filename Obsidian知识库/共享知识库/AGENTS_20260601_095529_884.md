## 一、子代理架构总览

### 1.1 子代理定义
子代理是拥有**独立上下文窗口**的专用AI助手，由主Agent通过 `/agents` 命令创建和调度，执行隔离任务后仅返回精炼结果。

### 1.2 核心价值
| 价值 | 说明 |
|------|------|
| 上下文隔离 | 每个子代理独立上下文，避免主对话膨胀 |
| 并行执行 | 多个子代理可同时处理不同子任务 |
| 专注高效 | 每个子代理聚焦单一领域，质量更高 |
| 安全边界 | 子代理权限可通过 allowed-tools 独立控制 |

### 1.3 何时使用子代理
- 任务可拆分为**独立可验证**的子任务
- 子任务执行过程**不需要**与主Agent实时交互
- 结果可**精炼汇总**，不需要完整执行日志
- 任务复杂度**值得**创建子代理的开销

### 1.4 反模式（何时不使用）
- 任务过于简单，委派开销大于直接执行
- 子任务间有紧密的实时依赖
- 需要主Agent全程参与决策的任务

## 二、子代理配置规范

### 2.1 创建子代理（`/agents` 命令）
```markdown
## 子代理：代码审查专家

### 触发条件
- 用户要求代码审查
- 提交PR前自动触发
- 代码变更超过50行

### 系统提示词
你是一个代码审查专家，专注于：
1. 代码质量和可读性
2. 潜在Bug和安全漏洞
3. 性能优化建议
4. 最佳实践遵循

### 权限
- 读取：当前项目所有文件
- 写入：仅审查报告文件
- 禁止：修改源代码、执行系统命令
```

### 2.2 子代理设计模式（R17核心新增）

#### 模式一：结构化输出格式
要求子代理以固定格式返回结果，确保可解析、可验证：
```
要求：以 JSON 格式返回，包含 status / summary / details / recommendations 字段
```

#### 模式二：障碍报告机制
子代理遇到无法解决的问题时**主动报告**，而非静默失败：
```
遇到以下情况时必须立即报告：
- 权限不足无法完成操作
- 依赖的外部资源不可用
- 结果质量低于阈值
```

#### 模式三：allowed-tools 权限限制
通过配置精确控制子代理可使用的工具：
```yaml
allowed-tools:
  - read_file
  - search_code
  - grep
# 显式排除：write_file, execute_command, delete
```

#### 模式四：Skills 注入
将Skills接入子代理，实现「隔离 + 专业化」双层架构：
- 子代理提供上下文隔离
- Skills提供领域专家能力
- 脚本执行不消耗子代理上下文

### 2.3 子代理分类
| 类型 | 特点 | 典型工具 |
|------|------|---------|
| 文件Agent | 文件系统操作 | read/write/list/search |
| 浏览器Agent | 网页交互 | navigate/click/extract |
| 应用Agent | 应用操作 | launch/install/interact |
| 系统Agent | 系统配置 | diagnose/repair/configure |
| 搜索Agent | 深度检索 | search/analyze/summarize |

### 2.4 权限矩阵
| 权限 | 文件Agent | 浏览器Agent | 应用Agent | 系统Agent |
|------|----------|------------|----------|----------|
| 读文件 | ✅ | 按需 | 按需 | ✅ |
| 写文件 | ✅ | ❌ | ❌ | 受限 |
| 网络访问 | ❌ | ✅ | ❌ | ❌ |
| 系统设置 | ❌ | ❌ | ❌ | ✅ |
| 应用控制 | ❌ | ❌ | ✅ | ❌ |

## 三、Skills 自动化配置

### 3.1 SKILL.md 模板
```markdown
---
name: 代码格式化
description: 按照项目规范自动格式化代码
trigger: 用户提到"格式化"或"format"
priority: 5
allowed-tools: [read_file, edit_file]
---

# 代码格式化 Skill

## 步骤
1. 检测文件语言和类型
2. 读取项目格式化配置（.prettierrc / .editorconfig）
3. 应用格式化规则
4. 验证格式化结果
5. 报告变更摘要

## 约束
- 不修改代码逻辑
- 保留原有注释
- 遵循项目已有风格
```

### 3.2 Skills 高级配置（R17新增）
| 配置项 | 作用 | 示例 |
|--------|------|------|
| `allowed-tools` | 限制工具访问 | `[read_file, edit_file]` |
| `trigger` | 触发条件描述 | "用户提到格式化" |
| `priority` | 优先级（多Skill冲突时） | `5`（数字越大优先级越高） |
| 脚本执行 | 不消耗上下文的复杂任务 | `scripts/format.sh` |

### 3.3 Skills 生命周期
```
创建 → 测试 → 评估 → 精炼 → 分发 → 废弃
```
- **创建**：编写SKILL.md和配套文件
- **测试**：在隔离环境中验证（含MCP Inspector测试）
- **评估**：Rubric评分，检查触发准确性
- **精炼**：根据评估结果优化
- **分发**：Git仓库 → plugins → 企业托管设置
- **废弃**：过时或低效的Skills标记废弃

### 3.4 Skills 与 Subagents 集成
- Skills可注入到自定义子代理中
- 子代理通过Skills获得领域专家能力
- 实现"子代理隔离 + Skills专业化"的双层架构
- **脚本执行不消耗子代理上下文**（核心性能优化）

## 四、Hooks 自动化配置

### 4.1 Hook 类型
| Hook | 触发时机 | 用途 |
|------|---------|------|
| PreToolUse | 工具调用前 | 权限检查、参数校验 |
| PostToolUse | 工具调用后 | 结果验证、日志记录 |
| PreMessage | 消息发送前 | 内容审查、格式标准化 |
| PostMessage | 消息接收后 | 自动处理、路由判断 |

### 4.2 配置示例
```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "delete|rm|format",
        "action": "confirm",
        "message": "检测到高风险操作，需要确认"
      }
    ],
    "PostToolUse": [
      {
        "matcher": "write_file",
        "action": "validate",
        "message": "验证文件写入完整性"
      }
    ]
  }
}
```

### 4.3 Hooks 三大用途（R17新增）
1. **格式化控制**：PreMessage hook 确保输出格式一致
2. **命令阻止**：PreToolUse hook 拦截高风险命令
3. **通知推送**：PostToolUse hook 完成后发送通知

## 五、MCP Server 自动化配置

### 5.1 标准MCP Server注册
```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@anthropic/mcp-server-filesystem", "/workspace"],
      "tools": ["read_file", "write_file", "list_directory"],
      "resources": ["file:///workspace/**"],
      "prompts": ["code_review", "refactor"]
    }
  }
}
```

### 5.2 MCP 三原语职责（R17更新）
| 原语 | 控制方 | 职责 |
|------|--------|------|
| Tools | 模型控制 | 执行操作（函数调用） |
| Resources | 应用控制 | 暴露只读数据（文件/API/DB） |
| Prompts | 用户控制 | 预构建指令模板 |

### 5.3 MCP 高级特性（R17新增）
- **Sampling**：MCP Server通过客户端请求LLM → AI成本从Server转移到Client
- **Progress Notifications**：长时操作实时进度 → context对象 + logging callbacks
- **Roots**：文件权限控制 → 特定目录授权 + 安全边界 + 用户友好文件发现
- **StreamableHTTP (SSE)**：服务器→客户端实时推送 → session管理 + 双连接架构
- **无状态HTTP**：水平扩展部署 → 负载均衡器 + 牺牲部分功能换取无限扩展
- **MCP Inspector**：浏览器端测试调试 → 替代手写JSON schema

### 5.4 传输选择决策树
```
本地开发/单机 → STDIO
远程服务/生产 → StreamableHTTP (SSE)
高并发/水平扩展 → 无状态HTTP + LB
```

## 七、Agent 生命周期管理

### 7.1 状态机
```
IDLE → RUNNING → WAITING → COMPLETED / FAILED
                      ↑__________|
```
- **IDLE**：等待任务分配
- **RUNNING**：执行任务中
- **WAITING**：等待用户输入或依赖完成
- **COMPLETED**：任务成功完成
- **FAILED**：任务失败，需人工介入

### 7.2 失败处理
| 失败类型 | 处理策略 |
|---------|---------|
| 工具调用失败 | 分析原因→调整参数→重试（上限2次） |
| 超时 | 检查点恢复→断点续传 |
| 权限不足 | 降级到更低权限操作→提示用户 |
| 依赖失败 | 等待依赖完成→超时后降级 |
| **障碍报告** | 子代理主动报告→主Agent决策→降级/重试/跳过 |

### 7.3 生产级扩展（R17新增）
- **Prompt Caching**：缓存优化 → 减少API延迟和成本
- **Extended Thinking**：深度推理模式 → 复杂任务专用
- **批量操作**：批量工具调用 + Web Search集成
- **GitHub 集成**：自动代码审查 + 版本控制工作流
