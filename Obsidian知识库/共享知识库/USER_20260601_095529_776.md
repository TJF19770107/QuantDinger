## 一、多Agent协作核心流程

### 1.1 任务接收与分解
```
用户需求 → 意图识别 → 领域匹配 → 子任务拆分 → Agent路由
```
1. **意图识别**：判断任务类型（文件/浏览器/应用/搜索/系统）
2. **领域匹配**：匹配最优Sub Agent（file-agent/browser/app-agent/computer-agent/search-agent）
3. **子任务拆分**：跨域任务按阶段分解，单域任务整体派发
4. **Agent路由**：明确先后依赖关系，确定执行顺序

### 1.2 单Agent闭环（推荐）
- 所有工作可合并在一次派发内完成时，**必须整包派发**
- Agent内部具备自主规划能力，无需外部指导步骤
- 正确：[派发File Agent] "找到周报并据此生成月报"
- 错误：先让File Agent找路径，再让其读取，最后再让其写文档

### 1.3 多Agent协作模式
| 场景 | 模式 | 示例 |
|------|------|------|
| 串行依赖 | A完成→B开始 | app-agent启动游戏→computer-agent调整配置 |
| 并行独立 | 同时派发 | 同时搜索多个来源 |
| 动态路由 | 基于结果决定 | 根据搜索结果决定下一步Agent |

## 二、Agent 调度标准

### 2.1 派发协议
```
<overall_goal> 用户原始完整需求 </overall_goal>
<current_task> 本次委托的具体任务 </current_task>
```
- `<overall_goal>` 始终保持用户原始完整需求不变
- `<current_task>` 仅写当前Agent需要完成的局部目标
- 结果导向：描述最终目标状态，不教导执行步骤

### 2.2 记忆传递机制
| 机制 | 用途 | 条件 |
|------|------|------|
| memory_ids | 传递历史工具结果 | 历史消息末尾有 `[memory_id: xxx]` 标记 |
| inherit_agent_id | 延续同名Agent对话 | 用户使用修正/回退类语言时 |

### 2.3 结果验收标准
- **验目标**：核对执行结果是否满足任务目标
- **验产物**：要求生成文件时，必须有真实文件路径
- **补缺口**：未完成目标时寻找其他Agent补全

## 三、Agent 协作最佳实践

### 3.1 上下文管理
- **精炼传递**：Agent间只传递必要结果，不传递完整执行过程
- **文件中介**：大批量数据通过文件系统传递，不占用上下文
- **记忆复用**：已获取的信息通过memory_ids传递，不重复获取
- **上下文管理命令**：`/compact`（压缩历史）/ `/clear`（清空重来）/ `/context`（查看状态）

### 3.2 错误处理
- **失败不盲重试**：分析失败原因后再调整策略
- **同类失败上限2次**：超出后降级或交还用户
- **优雅降级**：Agent失败时自动降级到Skill/Tool层
- **障碍报告**：子代理遇到无法解决的问题时主动报告，不静默失败

### 3.3 并行调度
- 无依赖的多个Agent调用**必须并行发起**
- 每轮并行上限5个
- 有数据/状态/安全依赖的必须顺序执行

### 3.4 子代理结构化输出（R17新增）
- 要求子代理以**固定格式**返回结果（JSON/Markdown表格等）
- 子代理必须声明 **allowed-tools** 限制
- 通过 `/agents` 命令快速创建自定义子代理

## 四、Claude Code 工作流集成

### 4.1 日常开发节奏
```
Explore → Plan → Code → Commit
```
- **Explore**：理解代码库、阅读相关文件
- **Plan**：生成执行计划，确认范围（Plan Mode 适合复杂任务）
- **Code**：编写/修改代码（Approval Mode 或 Auto-Accept）
- **Commit**：提交并记录变更

### 4.2 五大定制手段
| 手段 | 作用 | 粒度 |
|------|------|------|
| CLAUDE.md | 项目级记忆和约定 | 项目 |
| Subagents | 隔离上下文执行专项任务 | 任务 |
| Skills | 可复用指令模板（自动触发） | 操作 |
| MCP Servers | 连接外部系统 | 集成 |
| Hooks | 确定性检查点（格式化/阻止/通知） | 事件 |

### 4.3 Hooks 类型（R17新增）
| Hook | 触发时机 | 用途 |
|------|---------|------|
| PreToolUse | 工具调用前 | 权限检查、参数校验 |
| PostToolUse | 工具调用后 | 结果验证、日志记录 |
| PreMessage | 消息发送前 | 内容审查、格式标准化 |
| PostMessage | 消息接收后 | 自动处理、路由判断 |

## 五、MCP 集成流程

### 5.1 三层架构
```
Tools（执行）→ Resources（读取）→ Prompts（模板）
```
1. **Tools**：模型控制，让Agent执行操作（函数调用、API请求）
2. **Resources**：应用控制，让Agent直接访问数据（文件、数据库、API）
3. **Prompts**：用户控制，预构建的指令模板，标准化交互

### 5.2 传输模式选择
| 模式 | 适用场景 | 特点 |
|------|---------|------|
| STDIO | 本地开发、单机部署 | 标准输入/输出 + 初始化握手 |
| StreamableHTTP | 生产环境、远程服务 | SSE服务器推送 + 双连接架构 |
| 无状态HTTP | 水平扩展、负载均衡 | 牺牲部分功能换取无限扩展 |

### 5.3 高级特性（R17新增）
- **Sampling**：MCP服务器通过客户端请求LLM，成本从服务器转移到客户端
- **Progress Notifications**：长时操作的实时进度反馈
- **Roots**：文件系统权限控制，特定目录授权+安全边界
- **MCP Inspector**：浏览器端测试调试MCP服务器
- **装饰器SDK**：Python装饰器替代手写JSON schema，开发效率大幅提升

## 六、Claude Cowork 协作模式（R17新增）

### 6.1 Cowork vs Chat
| 维度 | Chat | Cowork |
|------|------|--------|
| 本质 | 对话（信息交换） | 工作会话（文件产出） |
| 产物 | 文本回复 | 真实文件结果 |
| 循环 | 一问一答 | 描述→计划→执行→引导 |
| 操作 | 仅生成文本 | 直接操作文件系统 |

### 6.2 Cowork 任务循环
```
用户描述任务 → Claude生成计划 → Claude执行操作 → 用户引导修正 → 产出文件
```

### 6.3 Cowork 应用场景
- Chrome 中驱动 Web 应用
- Word / Excel / PowerPoint / Outlook 插件
- 全局指令 + 项目上下文 + Skills + Plugins

## 七、API 开发工作流（R17新增）

### 7.1 全栈开发路径
```
API认证 → 提示工程 → 评估框架 → Tool Use → RAG → MCP → Agent架构
```

### 7.2 关键能力
- **Prompt Caching**：缓存优化减少延迟和成本
- **Extended Thinking**：深度推理模式
- **多模态处理**：图像分析 + PDF处理 + 引用生成
- **批量操作**：批量工具调用 + Web Search 集成

---

> 核心法则：专业的事交给专业的Agent，结果导向、记忆复用、失败降级。
> Chat是对话，Cowork是工作——前者问问题，后者出结果。
